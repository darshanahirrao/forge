# First application design

Subject: the ongoing work and native agents on one person's machine. Audience: someone who uses several harnesses every day. Job: reveal what needs attention, what can continue, and what is consuming capacity, with a direct path to the relevant work.

Treatment: a quiet operational interface. Keep the existing cool paper, ink, and teal identity. The distinctive choice is a persistent work list beside the attention and capacity view, so account or harness changes never displace the task. Detailed activity and context open in a sheet rather than taking the person out of the workspace.

## Tokens

- Cool paper `#F3F7F7`, the workspace ground.
- Panel white `#FFFFFF`, the work surface.
- Deep ink `#18343E`, text and navigation.
- Teal `#12665F`, the primary action and selected state.
- Slate `#4E666E`, secondary text.
- Structure `#B6C9CE`, boundaries and inactive controls.

Semantic warning and failure colors carry text labels as well as color. Dark mode reselects these tokens with measured contrast. Use Avenir Next or the local system sans-serif for headings and body; use the system monospace for identifiers, commands, and aligned accounting values. No remote fonts, imagery, or decorative charts are needed.

## Layout and content

Navigation follows work, approvals, accounts, resources, and connections. The overview starts with attention and a short factual summary, followed by tracked work and a compact capacity rail. A searchable command dialog reaches work and views. One primary action creates work. Each detail sheet shows source, current binding, context, chronological receipts, and applicable controls.

The real workspace opens with honest empty states and native installation discovery. A separate in-memory demo workspace contains fictional examples and is labeled throughout. Machine telemetry always identifies itself as live. Account slots are configured until a native identity check succeeds. Unknown quotas and costs stay unknown. Native capability limits appear beside the relevant action.

Every action has loading, failure, and keyboard states. Both themes and narrow screens must be rendered and checked. The application uses existing UI and server libraries and native harness execution; it does not implement a terminal, editor, browser, memory engine, or task reasoning loop.
